# TEAM_GUIDE.md

## Назначение проекта

`knowledge-base` — это не просто набор markdown-файлов, а управляемая база знаний с контролируемым циклом:

`inbox/ -> обработка -> kb/ru/ -> INDEX -> проверка -> публикация`

Главная цель — держать каноничную инженерную базу знаний по подшипникам и смежной продукции в чистом, масштабируемом и проверяемом виде.

## Карта слоёв

- `inbox/` — единственная точка входа для нового сырья.
- `inbox/processed/` — уже обработанные входные файлы.
- `kb/ru/` — каноничная база знаний.
- `kb/ru/INDEX.md` — центральный вход и навигационный индекс.
- `_templates/` — шаблоны статей и структурных документов.
- `_meta/` — реестры, аудит, дедуп, таксономия, служебные данные.
- `prompts/` — рабочие промпты и вспомогательные инструкции.
- `scripts/` — обработка inbox, quality gate, валидация, генерация.
- `tests/` — проверки ссылок и другие валидации.

## Главные правила

1. Сырьё не публикуется напрямую.
2. Канон живёт только в `kb/ru/`.
3. Одна статья = одна папка = один `README.md`.
4. Имена папок — ASCII kebab-case.
5. Метаданные обязательны.
6. Дубли не плодим.
7. Массовые рефакторинги без явной причины не делаем.

## Контракт статьи

Каждая статья должна опираться на `_templates/article.md`.

Минимальные поля front matter:
- `id`
- `title`
- `topic`
- `tags`
- `status`
- `source`
- `created`
- `updated`

## Статусы

- `draft` — рабочий черновик.
- `verified` — только проверенный материал без нерешённых дыр.
- `deprecated` — устаревший материал, если это соответствует текущей политике репозитория.

Если в статье остались `[[TBD]]`, неподтверждённые аналоги или спорные данные, такая статья не считается `verified`.

## Правила по структуре KB

- L1 и L2 — короткие навигационные страницы.
- L3 — конечные подробные страницы.
- Не создавать дубль одной темы под разными slug без явного решения.
- Не вводить новые верхнеуровневые разделы без реальной необходимости.

## Правила по slug

- Slug должен быть стабильным.
- Предпочтение — короткие смысловые slug на английском, если это уже принято в ветке.
- Перед переименованием slug проверять ссылки, индекс и реестр.
- Не делать массовые переименования ради красоты.

## Жёсткие правила по подшипникам

- Не выдумывать данные, аналоги, стандарты, суффиксы и размеры.
- Всегда отделять базовое обозначение от префиксов и суффиксов.
- Аналог допустим только при полном техническом совпадении.
- ГОСТ ⇄ ISO не выводить автоматически.
- Совпадение базового номера не считать доказательством аналога.
- При сомнении фиксировать ограничение, а не фантазировать.

Минимум проверок, где это релевантно:
- тип;
- геометрия;
- серия;
- исполнение;
- зазор;
- класс точности;
- уплотнение;
- сепаратор;
- префиксы/суффиксы.

## Как работать с inbox

1. Положить сырьё в `inbox/`.
2. По возможности сначала прогнать dry-run.
3. Не переносить вручную в канон без понимания темы, дублей и качества.
4. После обработки проверять, что результат действительно должен жить в `kb/ru/`.

## Команды проекта

```bash
python scripts/process_inbox.py
python scripts/process_inbox.py --dry-run
python scripts/kb_quality_gate.py
python scripts/validate_bearing_cards.py
python tests/check_kb_links.py
```

## Когда что запускать

- При intake и триаже — `process_inbox.py --dry-run`, затем при необходимости `process_inbox.py`.
- При структурных и контентных правках — `kb_quality_gate.py`.
- При изменении ссылок, slug, индекса — `tests/check_kb_links.py`.
- При карточках подшипников — `validate_bearing_cards.py`.

## Что нельзя делать

- Публиковать сырьё как канон.
- Маркировать как `verified` непроверенный материал.
- Смешивать overhaul структуры и мелкую правку контента в одном диффе без необходимости.
- Оставлять битые ссылки после переноса или переименования.
- Подменять техфакты общими словами.

## Как оформлять изменения

Предпочтительный порядок:
1. Прочитать релевантные файлы.
2. Понять, что меняется: intake, канон, индекс, slug, шаблон, метаданные.
3. Внести минимальный diff.
4. Прогнать релевантные проверки.
5. Коротко зафиксировать: что изменено, что проверено, какие ограничения остались.

## Практический принцип

Лучше маленький точный diff, чем большой красивый беспорядок.
Лучше честное `[[TBD]]`, чем убедительная ошибка.
Лучше один каноничный путь, чем два почти одинаковых.
